# Эксплуатация бота

Архитектура — `ARCHITECTURE.md`. Магазины на картах — `docs/STORES.md`.

## Диагностика «бот не отвечает»

По порядку, не перескакивая:

1. `/debug` в боте. Отвечает → проблема в конкретном сервисе, а не в боте.
2. Не отвечает вовсе → смотри логи Render: упал процесс или не встал webhook.
3. `TELEGRAM_BOT_TOKEN` задан? Без него приложение падает на старте намеренно.
4. Webhook: адрес должен быть `{RENDER_EXTERNAL_URL}/webhook`. После смены
   домена его надо переустановить — это делает `on_startup`, достаточно
   рестарта.
5. Пустые ответы AI → `GROQ_API_KEY` или лимит Groq (429 в логах).
6. Ответы без свежих данных → `SERPER_KEY` или исчерпана квота Serper.

## Правки кода

- Точка входа `bot.py` не переименовывается: на Render прописан `python bot.py`.
- Новая команда: обработчик в `teabot/handlers/`, регистрация в
  `register_handlers()`, кнопка — в `teabot/keyboards.py`, ветка в
  `on_cb` при необходимости.
- Новый внешний сервис: класс в `teabot/services/`, создание в
  `webapp.on_startup`, доступ через `bot_data` — глобальных переменных не
  заводить.
- Сервисы не знают про Telegram: форматирование и отправка только в
  обработчиках.

## Перед каждым пушем

```bash
python -m pytest -q
```

Тесты идут без сети. Если правка касается внешнего API — добавь тест на разбор
ответа с подменённой сессией (примеры в `tests/test_stores_providers.py`),
а не мокай весь клиент целиком.

## Деплой

1. Ветка → коммит → пуш → PR (черновик).
2. Render подхватывает ветку по настройке сервиса; после деплоя — `/debug`.
3. Новые переменные окружения задаются в Render до деплоя, иначе первый запуск
   отработает без них и придётся рестартовать.

## Известные ограничения

- Кэш и `user_data` живут в памяти процесса — при рестарте теряются.
- Состояние мониторинга отзывов лежит в файле, а диск Render эфемерен:
  после передеплоя первая проверка снова прогревочная.
- Обработка обновления идёт внутри HTTP-запроса Telegram — долгий поиск плюс
  LLM могут занять до ~40 секунд.

Эти три пункта решаются Redis и фоновой обработкой (этап 2 в `ARCHITECTURE.md`).
Предлагай их, только когда пользователь жалуется на симптом, а не заранее.
