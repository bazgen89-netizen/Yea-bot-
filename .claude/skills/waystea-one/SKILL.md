# WAYSTEA ONE — бот-агент для персонала

Цифровой сотрудник в Telegram: раздаёт задачи персоналу магазинов, принимает
подтверждения, напоминает, эскалирует владельцу и собирает отчёты.

Код — `waystea_one/`. Подробный разбор модулей — `waystea_one/README.md`.
Решения владельца, на которые ссылается код, — `docs/06_PROJECT_LOG.md`.

Это **не** чайный бот (`bot.py` + `teabot/`). Разные библиотеки и архитектура,
см. `CLAUDE.md`.

## Стек

aiogram 3 (polling) · PostgreSQL через SQLAlchemy async · APScheduler ·
Claude через `ANTHROPIC_API_KEY`. Точка входа — `app/main.py`.

## Четыре правила, которые легко нарушить

Каждое из них ломает бота тихо — тесты не падают, а поведение уезжает.

### 1. Порядок роутеров в `app/bot.py`

aiogram отдаёт сообщение **ровно одному** хендлеру. В `app/handlers/shift.py`
стоит общий `F.text` catch-all, поэтому всё специфичное регистрируется до него:

```
tasks → owner → tea_requests → shift (catch-all последним)
```

Новый роутер с конкретным условием добавляй **перед** `shift_router`, иначе он
никогда не сработает.

### 2. Один текстовый хендлер — вся цепочка внутри

Из-за правила 1 разбор текста сотрудника живёт внутри `shift.py`: «готово» по
задаче, заявка на закупку, отчёт по выручке, упоминание апсейла, вопрос в базу
знаний. Порядок проверок в цепочке — в докстринге модуля. Добавляя новый тип
сообщения, встраивайся в эту цепочку, а не заводи отдельный `F.text`-хендлер.

### 3. FSM — `GLOBAL_USER`, не по чату

Диалоги «как зовут → какой магазин» начинаются в группе, а продолжаются в
личке. Состояние скоплено по пользователю (`FSMStrategy.GLOBAL_USER`). Не
переводи на разбивку по чатам — многошаговые диалоги потеряются.

Все ответы сотруднику уходят в личку через `app/services/messaging.py`, а не
туда, откуда он написал. Telegram не даёт боту писать первым, поэтому есть
разовый фолбэк-пинг в группу.

### 4. AI-слои падают наружу, а не блокируют

`ai.py`, `vision.py`, `intent.py` — fail-open: нет ключа или API ответил
ошибкой → работаем как раньше (фото принимается, магазин уточняется вопросом),
а не стопорим сотрудника. Сохраняй этот контракт в любых правках AI-слоя.

## Как устроена выдача задач

Все задачи на день создаются сразу, но показываются **батчами**: по решению
владельца сначала 3 простых, потом по 3–5. Номер батча — поле `batch` на
`TaskTemplate` (то есть меняется в `scripts/seed_task_templates.py`, а не
константой в коде); показывается сразу только самый младший батч, остальные
лежат с `sent_at=None`. Следующий батч открывается, когда текущий закрыт
полностью (`advance_to_next_batch()` в `app/services/tasks.py`).

Отсюда важное: **напоминания считаются от `sent_at`, не от `created_at`**.
Задача из ещё не показанного батча не должна «стареть». Напоминания — через 30
и 60 минут (`FIRST_REMINDER_MINUTES` / `SECOND_REMINDER_MINUTES`), после двух
проигнорированных идёт эскалация владельцу.

Правка шаблонов задач — `scripts/seed_task_templates.py`. Сидеры идемпотентны и
запускаются на каждом старте из `app/main.py`, потому что на бесплатном Render
нет шелла для ручного запуска. При изменении шаблона уже открытые задачи
подтягиваются автоматически: `sync_stale_tasks_to_templates()` на старте
пересинхронизирует `requires_proof` / `proof_type` / `verification_criteria`,
чтобы сотрудник не застрял на требовании, которого в чек-листе больше нет.

`TaskTemplate.description` — то, что видит сотрудник под названием задачи.
`verification_criteria` — внутреннее поле, только для AI-проверки фото.

## Расписание (APScheduler, `app/main.py`)

- напоминания, апсейл-подсказки, музыкальные проверки — интервал
  `REMINDER_POLL_SECONDS`
- отчёт владельцу — `DAILY_REPORT_HOUR:DAILY_REPORT_MINUTE`
- напоминания о выручке — 20:55 (Гагарина, Черёмушки) и 21:55 (Рынок на
  Студёной): второй магазин закрывается позже

Все `CronTrigger` берут таймзону **явно** из `settings.timezone`. Без этого
APScheduler возьмёт время сервера (на Render — UTC) и часы уедут. Добавляя
новую cron-задачу, обязательно передавай `timezone=settings.timezone`.

## Проверка фото

`app/services/vision.py` умеет сверять фото с `verification_criteria` через
Claude. **Сейчас не используется**: по решению владельца все шаблоны в
`seed_task_templates.py` идут на комментариях, пока не готовы эталонные фото.
Текст критериев в шаблонах сохранён — вернуть задачу на фото это правка
`ProofType` в одну строку.

## Перед пушем

```bash
cd waystea_one && python -m pytest -q
```

39 тестов, идут без БД, токена и ключа Anthropic — `tests/conftest.py`
подставляет фиктивные переменные окружения. Покрыта чистая логика
(`store_matcher`, `shift_detector`, `purchasing`, `revenue`, `upsell`,
`question_detector`) и фолбэки AI-слоя. Правишь разбор текста — добавляй тест
туда же, живой сети в тестах быть не должно.

## Эксплуатация

Хостинг — Render, бесплатный Web Service. Отсюда три особенности, каждая
намеренная:

- `app/health.py` поднимает HTTP-порт **первым**, до `init_models` и сидеров:
  Render ждёт ответ на `$PORT` быстро после старта, иначе считает сервис
  упавшим.
- `waystea-keep-alive.yml` пингует health каждые 10 минут — бесплатный тариф
  засыпает после ~15 минут без трафика.
- `delete_webhook(drop_pending_updates=True)` на старте: без этого частые
  рестарты Render заставляли бота переобрабатывать backlog и слать
  приветствие по нескольку раз (а в онбординге чужое сообщение попадало в
  поле «имя»).

Чтобы бот видел обычные сообщения в группе, ему нужен админ-статус или
выключенный Privacy Mode (@BotFather → Bot Settings → Group Privacy).

Каждый сотрудник должен один раз открыть личный чат с ботом и нажать Start,
иначе бот не сможет ему написать.

## Известное расхождение

Дефолт таймзоны в `app/config.py` — `Europe/Moscow`, а комментарий в
`app/main.py` говорит `Asia/Almaty`. На проде значение задаётся переменной
`TIMEZONE`, так что на поведение не влияет, но при правках расписания сверься
с фактическим значением, а не с комментарием.
