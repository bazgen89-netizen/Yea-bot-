# Сервер склада

Общая база для приложения «Склад»: одни и те же товары, остатки и продажи на
всех устройствах, сотрудники с разными правами, несколько точек и открытый API
для интеграций.

Приложение продолжает работать без интернета — сервер нужен, чтобы данные
сходились между устройствами, а не чтобы касса зависела от связи.

## Быстрый запуск

Нужен Docker.

```bash
cd warehouse-server
cp .env.example .env
# впишите POSTGRES_PASSWORD, например: openssl rand -base64 24
docker compose up -d
```

Проверить, что поднялось:

```bash
curl http://localhost:3000/health
```

Документация API открывается в браузере: <http://localhost:3000/docs>

Создать организацию и владельца:

```bash
curl -X POST http://localhost:3000/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"org_name":"Waystea","name":"Ваше имя","email":"you@example.com","password":"длинный-пароль"}'
```

В ответе придёт `token` — им авторизуются все дальнейшие запросы.

> После того как завели свою организацию, поставьте `ALLOW_REGISTRATION=false`
> в `.env` и перезапустите (`docker compose up -d`). Иначе любой, кто знает
> адрес сервера, сможет создать у вас аккаунт.

## Развёртывание на сервере

Подойдёт любая площадка, где есть Docker: Yandex Cloud, Timeweb, Selectel,
обычная VPS.

1. **Возьмите виртуальную машину.** Для магазина хватает 1 ядра и 1 ГБ памяти.
2. **Установите Docker** по инструкции площадки.
3. **Скопируйте папку** `warehouse-server` на сервер (`git clone` или `scp`).
4. **Заполните `.env`** — обязательно свой `POSTGRES_PASSWORD`.
5. `docker compose up -d`

**Обязательно поставьте HTTPS.** Токены ходят в заголовке запроса: по HTTP их
может прочитать любой на пути. Самый простой способ — nginx или Caddy перед
сервером, с бесплатным сертификатом Let's Encrypt.

**Порт базы наружу не открыт** — в `docker-compose.yml` он намеренно не
публикуется, база доступна только серверу приложения.

### Управляемая база вместо контейнера

Если берёте PostgreSQL как услугу (Yandex Managed PostgreSQL и подобное),
уберите сервис `db` из `docker-compose.yml` и укажите:

```
DATABASE_URL=postgres://пользователь:пароль@хост:6432/warehouse
```

Такие базы требуют TLS и часто отдают собственный корневой сертификат — тогда
добавьте `PGSSL_ALLOW_SELF_SIGNED=true`.

## Перенос данных из другой программы

Товары и клиентская база переносятся выгрузками Excel. Оба скрипта сначала
показывают, что разобрали, и **без `--token` ничего не записывают** — так можно
проверить файл до загрузки.

### Каталог

```bash
node scripts/import-catalog.mjs каталог.xlsx                       # только разбор
node scripts/import-catalog.mjs каталог.xlsx --token $TOKEN        # загрузка
```

Колонки ищутся по заголовку: `Наименование`, `Код`, `Артикул`,
`Единица измерения`, `Цена продажи`, `Скидка` и любое число колонок вида
`Название магазина (Остаток)`. Магазины из заголовков заводятся сами,
`Общий остаток` пропускается — это сумма остальных.

Остатки проставляются инвентаризацией: в выгрузке лежит итог, а не приход.
Отрицательные переносятся как есть — иначе картина не совпадёт с тем, что было.

### Клиенты и поставщики

```bash
node scripts/import-clients.mjs клиенты.xlsx --token $TOKEN
node scripts/import-clients.mjs поставщики.xlsx --kind supplier --token $TOKEN
```

Колонка с именем обязательна (`Наименование`, `Имя`, `ФИО`, `Клиент`…),
остальные — по желанию: телефон, почта, комментарий, тип.

Человек опознаётся по **последним десяти цифрам телефона**: `+7 999 123-45-67`
и `8 (999) 1234567` — один и тот же номер. Телефона нет — опознаём по имени.
Тёзки с разными номерами остаются разными людьми.

Повторная загрузка того же файла ничего не портит: карточки обновляются,
дубли не появляются, а пустые поля в выгрузке не затирают заполненные в базе.

## Резервные копии

Данные — самое ценное, что здесь есть. Настройте копирование сразу.

```bash
./scripts/backup.sh                                   # копия прямо сейчас
./scripts/restore.sh backups/warehouse-....dump       # восстановление
```

Ежедневно в 4 утра — добавьте в `crontab -e` на сервере:

```
0 4 * * * cd /путь/к/warehouse-server && ./scripts/backup.sh
```

Копии складываются в `./backups` и хранятся 30 дней. **Увозите их с сервера** —
копия рядом с базой не спасает от потери самого сервера.

## Открытый API

- **Документация:** `/docs` — страница со всеми эндпоинтами
- **Машинное описание:** `/api/v1/openapi.json` — OpenAPI 3.1, годится для
  генерации клиента

**Единицы.** Деньги — целые копейки (`50000` = 500,00 ₽), количества — целые
тысячные (`1500` = 1,5 кг). Дробных чисел в API нет: на длинных чеках они
накапливают ошибку округления.

**Ключи интеграций.** Владелец выпускает ключ с правами `read` или
`read` + `write`:

```bash
curl -X POST http://localhost:3000/api/v1/api-keys \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Сайт","scopes":["read"]}'
```

Ключ (`whk_...`) показывается **один раз** — в базе лежит только его хеш.
Дальше он работает вместо токена:

```bash
curl http://localhost:3000/api/v1/products -H "Authorization: Bearer whk_..."
```

Отзывается без смены паролей: `DELETE /api/v1/api-keys/{id}`.

## Права ролей

| | Владелец | Продавец | Ключ `read` | Ключ `write` |
|---|---|---|---|---|
| Смотреть товары и остатки | ✅ | ✅ | ✅ | ✅ |
| Видеть закупочные цены и прибыль | ✅ | ❌ | ✅ | ✅ |
| Продавать и оформлять возврат | ✅ | ✅ | ❌ | ✅ |
| Заводить и править товары | ✅ | ❌ | ❌ | ✅ |
| Приход, списание, инвентаризация | ✅ | ❌ | ❌ | ✅ |
| Отчёты | ✅ | ❌ | ✅ | ✅ |
| Сотрудники и ключи | ✅ | ❌ | ❌ | ❌ |

Закупочные цены не просто скрыты в интерфейсе — сервер вырезает их из ответа.
Прятать такие поля только на экране бессмысленно: данные всё равно уехали бы
на устройство.

## Как работает синхронизация

Устройство помнит номер последнего полученного изменения и работает двумя
запросами.

**Забрать чужие изменения:**

```
GET /api/v1/sync/pull?since=<последний номер>
→ { changes: {...}, cursor: 812, has_more: false }
```

**Отдать свои:**

```
POST /api/v1/sync/push
{ "products": [...], "sales": [...], "stock_moves": [...] }
→ { cursor: 815, applied: { "sales": 2 } }
```

Правила слияния намеренно разные:

- **Справочники** (точки, категории, товары, контрагенты) изменяемы. Побеждает
  более поздняя правка: сервер сравнивает `updated_at` и не даёт старой версии
  перетереть свежую.

  > **Чего пока не хватает.** Отметку `updated_at` присылает только карточка
  > товара; у точек, категорий и клиентов её в приложении нет вовсе, и для них
  > «более поздняя правка» на деле означает «позже отправленная». Пока
  > устройства синхронизируются часто, разницы не видно, но телефон,
  > пролежавший офлайн неделю, свою старую карточку клиента всё же навяжет.
  > Чинится отметкой времени правки на этих таблицах в приложении.
- **События** (документы, движения, чеки) неизменяемы. Их не сливают — их просто
  не вставляют дважды. Идентификатор придумывает телефон, поэтому повторная
  отправка того же чека ничего не меняет.

**Продажа с телефона не проверяется на остаток.** Она уже случилась: товар
отдан, деньги взяты. Отклонить её значило бы потерять выручку из учёта. Если
из-за офлайна остаток ушёл в минус, это видно в отчёте и правится
инвентаризацией.

## Помощник: вопрос словами

`POST /api/v1/assistant/ask` превращает вопрос обычными словами в запрос к
складу:

```
POST /api/v1/assistant/ask
{ "question": "какие товары кончаются?",
  "schema":   "products — Товары.\n  колонки: id, name, sale_price\n\n…" }
→ { "sql": "SELECT …", "comment": "Смотрю остатки: сумма движений по товару." }
```

**Данные магазина сервер здесь не читает вовсе.** Наружу, к модели, уходит
только вопрос и описание таблиц — названия таблиц и колонок, которые присылает
само устройство. Считает по возвращённому запросу устройство, у себя, по своей
базе. Поэтому на вопрос «кто из клиентов давно не заходил» ответ будет, а
список имён при этом не увидит никто посторонний.

Это не только про закон о персональных данных. Это то, что честно сказать
магазину, который спросит: «а вы мою базу никому не отдаёте?»

Ключ живёт на сервере, а не в приложении: приложение — это файл, который
скачивает каждый, и ключу в нём не место.

| Переменная         | Что задаёт                                        | По умолчанию                             |
| ------------------ | ------------------------------------------------- | ---------------------------------------- |
| `ASSISTANT_KEY`    | Ключ модели. **Без него ручка отвечает 503** и говорит, чего не хватает. | — |
| `ASSISTANT_KIND`   | `claude` или `openai` (так говорит и ДипСик).      | `claude`                                 |
| `ASSISTANT_URL`    | Адрес модели.                                      | `api.anthropic.com` / `api.deepseek.com` |
| `ASSISTANT_MODEL`  | Название модели.                                   | `claude-opus-5` / `deepseek-chat`        |

Переключиться с Клода на ДипСик — это две переменные, а не другой код:

```bash
ASSISTANT_KIND=openai
ASSISTANT_KEY=<ключ ДипСика>
```

Запрос от модели выполняется **только на чтение**: приложение проверяет его до
базы — одна команда, только `SELECT` или `WITH`, ничего из того, что меняет
данные. Запрос при этом всегда показывается человеку целиком: ответ, которому
нельзя заглянуть внутрь, — не ответ, а гадание.

## Устройство кода

```
warehouse-server/
├── src/
│   ├── db/          интерфейс к базе, драйвер PostgreSQL, схема и миграции
│   ├── auth/        пароли (scrypt), сессии устройств, ключи интеграций
│   ├── core/        логика: каталог, склад, продажи, отчёты, синхронизация
│   ├── http/        маршруты, права, вырезание закупочных цен
│   ├── openapi.ts   описание API
│   └── server.ts    сборка приложения
├── scripts/         резервные копии
├── test/            тесты на PGlite
├── Dockerfile
└── docker-compose.yml
```

Весь SQL пишется против тонкого интерфейса `SqlDb`. На проде под ним настоящий
PostgreSQL, в тестах — PGlite (PostgreSQL, собранный в WebAssembly). Один и тот
же SQL, но тесты не требуют поднятой базы.

## Ключевые решения

**Идентификаторы — UUID, а не автоинкремент.** Телефон создаёт товар и чек, ещё
не имея связи с сервером, и должен сразу знать их идентификаторы. Автоинкремент
на двух телефонах дал бы столкновения.

**У каждой строки есть `seq`** — номер в общей очереди изменений организации.
Устройство помнит последний полученный номер и просит «всё, что больше».
Не нужно сравнивать содержимое — достаточно сравнить числа.

**Остаток не хранится числом.** Он всегда `SUM(stock_moves.qty_delta)` по
товару и точке. Рассинхронизировать остаток с историей невозможно.

**Себестоимость чека берётся из карточки товара**, а не из присланной клиентом:
устройство продавца её не видит, и доверять этой цифре нельзя — от неё считается
прибыль.

**Ничего не удаляется физически** — только флаги `archived` и `deleted`. Иначе
телефон, неделю бывший офлайн, никогда не узнает, что запись исчезла.

**В базе только хеши токенов.** Пароли — через scrypt (медленно, специально),
токены — через SHA-256 (быстро, потому что проверяются на каждом запросе, а
перебрать 32 случайных байта нечем).

**Ссылки проверяются на принадлежность организации.** Внешние ключи в базе
смотрят на таблицу целиком, поэтому клиент, угадавший чужой идентификатор
точки, иначе привязал бы к ней своё движение.

**Node исполняет TypeScript напрямую** — шага сборки нет, и между тем, что
протестировано, и тем, что запущено, нечему разъехаться.

## Проверки

```bash
npm install
npm test          # 141 тест на настоящем PostgreSQL
npm run typecheck
```

Что покрыто: арифметика чеков, приход, списание, инвентаризация, перемещение
между точками, откат документа при ошибке в середине, запрет продажи сверх
остатка, возвраты, отчёты, права каждой роли на каждом эндпоинте, повторная
синхронизация, слияние правок каталога, изоляция организаций друг от друга.

Тесты запускаются автоматически на GitHub при изменениях в `warehouse-server/`.
